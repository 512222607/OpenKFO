# 游戏服务端：奖励、道具与玩家背包

## 职责与依赖

任务/战斗/训练/成长业务负责判断资格和选择奖励；道具定义负责解释物品模板；背包负责玩家持有实例。GM是独立管理入口，不是游戏发奖依赖。

```text
任务 / 战斗结算 / 训练 / 称号领奖
    ├─ 核实资格、读取规则、检查该业务领取记录
    ├─ RewardManager.GrantProgressItems：经验/金币、升级礼包和领取记录（内部调用 GrantProgress）
    └─ RewardManager.GrantItem：读取独立物品定义、取得模板及期限
              └─ InventoryManager.AddItem：实例编号、入库、到期记录
商城购买 / 邮件领取 ── 校验交易或附件 ──┘
```

每个业务持有一个数据库事务：账号锁、资格、发放、完成记录一起提交；提交成功后游戏层发送原有协议。共用函数不得自行提交，不得在事务内向客户端发成功通知。保留各业务已经验证的幂等键，不再引入第二套领取账本。

## 背包数据约定

- 物品定义ID与玩家物品实例ID分开。同一种武器可以有多条实例；跨玩家不能凭实例ID获取他人物品。
- 玩家实例沿用inventory的(uid,instance)主键及原生68B记录；装备位置保存在记录+17，期限使用inventory_expirations。客户端记录布局集中在协议层及现有物品函数中。
- 公共发放不会自动装备或擅自合并实例；装备和消耗各有规则。此次不改变数量/叠加语义。
- 经验卡入包与使用后增加经验是两个动作；宠物入包与宠物成长/出战也不能混为一谈。
- 成长称号的角色等级字段与类型31称号物品分别处理；物品称号走背包，不能写进成长称号字段。
- 初始角色装备和历史数据导入保留已有实例布局；GM审计、修复和VIP管理路径仍独立，未改动。

## 新增奖励的接入规则

1. 在对应业务配置中定义奖励；资格和数量由服务器决定，不接受客户端提交库存记录。
2. 在业务原有事务中锁定账号、检查领取记录，然后调用公共进度/库存函数。多个奖励使用同一事务。
3. 写入完成记录再提交；重复请求返回已记录结果，不再随机、不再插入物品。
4. 游戏层在成功提交后通知库存、经验和余额变化；结算、任务、邮件继续使用各自原生UI协议。

## 尚未扩展的能力

- 升级礼包已接入；宠物培养、称号多槽和经验卡使用业务仍未新增。
- 奖励定义已独立为 item_definitions；商城上下架、改价及售卖期限不再改变奖励定义。
- 战斗掉落仍保留现有仅武器、原有期限规则；扩展其他类型需要明确配置及使用规则，不在结构重构时隐式开放。
- 各功能仍使用现有的客户端通知协议；没有把“背包写入”误当成所有道具玩法已可用。

## 验证

独立debug库测试通过：普通任务、扩展任务、称号领奖、邮件重试、购买期限、训练领取、战斗掉落重试、成长结算。新增测试覆盖批量发放回滚、实例唯一、期限同事务、模板不变、金币/经验溢出不修改档案。部分测试使用连接级临时表，其余使用独立测试账号并清理；没有修改现有玩家奖励。

## Manager 命名与入口

Go 对外可用的类型和方法首字母大写，例如 `RoleManager.AddExp`；包名仍为小写 `persistence`。Manager 共享 Store 的连接池，使用 `store.RoleManager()` 等方法取得，不维护另一份玩家状态。

| Manager | 已承接职责 / 方法示例 |
| --- | --- |
| RoleManager | 角色档案、创建与改名；AddExp、SetLevel、Snapshot、CreateCharacter |
| InventoryManager | 玩家背包实例发放、消耗、到期；AddItem、Consume、ExpireInventory |
| EquipmentManager | 装备位置、所有权与同槽替换；Equip、EquipDefault |
| RewardManager | 奖励配置、公共发奖及新手引导奖励；GrantProgressItems、GrantProgress、GrantItem、CompleteTutorial、BattleRewards |
| WalletManager | 点券调整及幂等记录、加款边界；AdjustTickets、CreditBalance |
| ItemManager | 已实现的武器强化、法宝使用/修复及对应配置 |
| TitleManager | 成长称号与称号奖励领取 |
| TaskManager | 普通与扩展任务状态、完成和领取 |
| BattleManager | 整场结算、结算回执、战斗流水编号 |
| ShopManager | 商城目录、购买和 VIP 商城价格配置 |
| MailManager | 赠送、邮箱、附件领取 |
| TrainingManager | 训练进度、领取、排名和规则 |

`AddExp` 在调用方锁定的档案上计算经验、连续升级和累计经验，返回升级前后等级；上限为 `MaxRoleLevel`。`SetLevel` 是显式等级修正，要求同时提供剩余经验，不冒充经验奖励，也不自动发升级礼包。两者都不自行保存数据库或发送协议。新增礼包由外层业务在同一事务内根据等级变化发放并记录，不能在加经验函数中递归发奖。

`GrantProgressItems`、`GrantItem`、`AddItem` 为组合事务入口（`GrantProgress` 仅作进度计算）；资格检查、业务回执、库存及余额必须在调用方同一事务中提交。`Equip`、`Purchase` 等完整业务入口保留自己的事务。不要在已有事务里再调用会另开事务的入口。

房间/连接仍由现有游戏 Hub 管理，未为其增加空壳 Manager。Store 保留连接、建表、认证、管理入口及尚未迁移的业务。宠物业务未确认，因此没有建立假实现的 PetManager。

## 协议与业务数字

已确认的协议号、房间模式、物品类别与槽位集中在 `internal/protocol/names.go`，数值显式固定，避免枚举插入时改变原生协议。

```go
if room.Type() == protocol.TeamSurvival {
    // 团队生存模式
}
if room.Type().IsTeam() {
    // 团队生存或团队死亡竞赛
}
// protocol.MsgRoomEntered    // 3100，进入房间
// protocol.MsgSDKLoginResponse // 1002，SDK 登录响应
// protocol.ItemWeapon         // 25，武器类别
// protocol.SlotPrimaryWeapon  // 8，主武器槽
```

`Room.Type()` 从权威房间请求中读取类型，不额外保存容易与房间修改不同步的 Type 字段。原始字节和类型转换保留在协议边界。测试可保留数字作为线格式证据。尚未确认的消息、布局字段和物品类别不能凭猜测命名；常量存在也不表示新增了对应玩法（例如装饰称号的装备支持）。

## 独立物品定义与升级礼包

- `item_definitions` 保存 `definition_key / revision / record / days`，没有指向商城的外键。首次启动迁移旧商品的发放模板和服务器期限，包含下架商品，保留原编号。以后只补缺失定义，不覆盖既有定义；新建商城条目只初始化其缺失定义。不要直接删表后把迁移当作配置恢复工具。
- 旧任务 `reward_catalog`、称号选择和掉落 `catalog_key` 字段为兼容存档保留原名，含义已是物品定义编号；武器ID、物品定义编号、玩家背包实例ID是不同字段。
- 商城购买和付费赠送仍用其销售模板、数量及售卖期限；任务、称号和升级礼包读取独立定义。独立定义编辑不修改商品价格或现有背包实例。战斗武器掉落沿用此前的期限语义（AddItem 的服务器期限为0），不在本次迁移中改变。
- GM 的“战斗奖励 → 奖励物品定义”支持读取、修改服务器期限、复制为新的奖励规格；复制的新编号无需上架。模板保留原生数量和客户端字段。`definitions_get / definition_save` 通过既有认证与环境选择，保存使用 revision 防止并发覆盖。
- GM 的“升级礼包”配置 `level_gifts`，每项包含到达的 `level` 和 `items` 定义编号列表。每级1–8件、2–150级、合计最多150件；重复的物品编号代表多件独立实例。空列表不发礼包。等级1的新角色初始物品仍属创建角色流程。
- 战斗、普通任务、扩展任务、训练奖励均调用 `GrantProgressItems`，一次跨多级逐级处理。`level_reward_receipts` 的 `(uid,level)` 唯一键与账号锁防止重复发放；领取记录、背包、到期记录和角色进度在同一事务提交。
- 到达过的等级不因改礼包配置补发；降级后再次到达已记录等级也不重复发。升级礼包不授予额外经验，避免递归升级。直接调用 `RoleManager.SetLevel` 是等级修正，不发礼包。
- 缺失或无效物品定义使整次业务回滚，不跳过坏奖励、不只扣款/只加经验。各业务原有回执继续控制重试，提交成功后通过库存通知更新客户端。
- 旧 GM 请求缺少 `level_gifts` 时保留既有礼包；新版传空数组可明确清空。成长 CSV 仍仅包含原来的8列，不覆盖礼包和掉落配置。本地复制到线上会展示礼包差异，但物品定义不会自动复制；目标环境必须先具备对应定义。

已验证：独立测试库中下架任务发奖、定义迁移不覆盖、商城删除后仍可使用定义、跨级多件礼包、迟发失败全回滚、降级重升不重复、期限原子写入、配置修订冲突，以及旧 GM 保存保留礼包。游戏客户端的实际通知显示仍需实测。


## 引导与多类型成长奖励

`RewardBundle` 统一表达物品定义列表、金币、点券。`RewardManager.GrantBundle` 在调用者的账号行锁事务中发放；升级继续用 `(uid,level)` 回执，原生引导 `4124` 使用 `tutorial_rewards(uid)` 回执。失败不推进角色称号或部分入账，已完成角色不追补新配置。

引导完成按服务器档案 +123 推进到称号2。必须先发送4125/64同步客户端称号，再发送2160库存通知、1240金币、1230点券、3115退出和完成提示。实测移除4125后，客户端在3115后约100ms再次上行3010，不能延迟到下次加载资料才同步。原生4125还会触发称号/武器选择界面，此界面与GM自动发放的奖励包不同，空候选界面仍需单独处理；未伪造可领取资格。已完成角色的延迟3010只修复本地称号并返回大厅，不创建新房。

GM 按 `item.txt` 名称与68B定义的类别/物品ID匹配，不要求输入ID。独立新定义由后端校验客户端目录生成，保存奖励时再次校验引用。战斗掉落仍限武器；装饰称号使用类型31库存记录，未假定已实现多称号装备。

# 好友协议（原生 SDFriend）

2026-09-20：根据当前客户端 `SDFriend.dll`、`gfld.dat` 及真实 8020 请求实现。
证据见 [native-wire.asm](nixiang/friends/native-wire.asm)。本页不把结构体内存偏移当作网络偏移。

## 封装

外层消息 8020；载荷前 4 字节为 `u16 LE 子消息号 + 0 + 扩展头长度`。
当前服务器仅接受两个头标志均为 0 的请求。其余字段中，整数及字符串长度使用大端；字符串为 `u16 BE 字节长度 + GBK 字节`，不含 NUL。
名字最多 20 字节，留言最多 199 字节，严格消费整个请求，不接受截断、尾随数据及无效编码。

| 客户端请求 | 请求体（4B头之后） | 服务器响应 |
|---|---|---|
| 203 初始化 | 1B 标志，0或1 | 204：u32 BE 结果1；随后226全表 |
| 207 添加 | 名字字符串、留言字符串 | 212：u32 BE 结果1、目标名字；随后226全表 |
| 213 删除 | 名字字符串 | 214：u32 BE 结果1、目标名字；随后226全表 |
| 225 列表 | u32 BE 本地版本 | 226全表；当前不使用增量版本 |

失败时使用现有游戏文字通知，不伪造未知的原厂错误码。失败不创建关系，不返回成功包，不断开游戏连接。
不支持的子协议明确提示；群组、黑名单和私聊不在本次实现范围内。

真实添加 `qqq` 请求：`cf000000 0003 717171 0000`。
成功响应：`d4000000 00000001 0003 717171`。

## 列表 226

4B头之后依次为：

1. u8 类型11（完整好友列表）。
2. u32 BE 版本0、u16 BE 好友数量（最多100）、u8 自定义分组数量0。
3. 每位好友：u8 状态（1离线、2在线）、u8 分组0、名字字符串。
4. 每位好友的34B资料：u32 BE UID高位、u32 BE UID低位、26B可选资料（当前未确认语义，置0）。
5. u16 BE 附加列表数量0。即使类型11也必须带这个字段，DLL解码器会读取两部分。

空表仍然返回完整结构（共14B），不能以零长度载荷代替。在线状态在读取列表时依据认证会话、游戏频道和连接存活状态计算；没有额外的自动上线/离线推送。

## 原生消费链与业务边界

- `gfld!A26FB0 -> 99DD00 -> SDFriend vtable+44 -> 10002660 -> 100010B0`。
- DLL `10009B60` 注册子协议编码/解码，`1000A230/A290` 处理网络序整数，`1000A3B0/A440` 处理变长字符串。
- 212：DLL `10001910` -> observer+28 -> `gfld!99D4D0`；结果1才插入好友UI。
- 214：DLL `10001950` -> observer+2C -> `gfld!99D370`；结果1才移除。
- 226：`10001440 -> 100014C0 -> 100029F0`；结构体资料36B因对齐而比网络资料34B大。
- 当前8020对象的observer由 `gfld!99D040` 安装表 `BA5C70`；208的observer+10是 `99CEC0` 空函数。与另一个社交对象的邀请确认流程不同，本实现采用原生可用的单向好友列表，不自动修改对方列表、不发送无法消费的确认邀请。

## 持久化与校验

`FriendManager` 管理 `friends(uid, friend_uid)` 表，复合主键及外键防止重复、悬空关系。仅认证会话UID作为所有者；精确角色名匹配，重名旧数据拒绝。禁止添加自己、无角色账号、不存在账号；数量上限100。

按UID顺序锁定两个账号，在事务内重新核对角色，执行存在性、容量检查与增删。并发同向/反向操作使用一致锁序；重复添加和删除均幂等。角色重置期间不把无效角色显示为好友。

## 验证边界

Go测试覆盖真实捕获请求、畸形包、中文名字、完整列表边界和字节序。独立测试库覆盖并发重复请求、容量、所有者隔离、单向关系、数据库重开恢复；游戏分发集成测试覆盖添加、删除、在线/离线查询及会话重登。
这些不等于原生客户端界面已验收；上线后仍需检查好友列表实际显示。

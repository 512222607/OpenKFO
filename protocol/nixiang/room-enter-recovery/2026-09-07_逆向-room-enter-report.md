# 创建房间和进房协议修正

本轮核对的是用户本地隔离客户端与已重建的实验服务端。旧版服务收到创建请求后只回 `3020/4`，客户端没有进入真实房间初始化。原因是从原始内存镜像解析消息分发表时，既混淆了记录字段顺序，又遗漏了表中绝对指针到文件偏移的 `0x10000` 换算，最终把其他功能的处理函数认成了建房函数。本轮已实现有证据支持的 `3020/83` 和 `3100/245` 链路，移除错误固定回包。真实客户端已发出3070并收到3100，用户明确确认“已经进入房间”。随后发现的3550状态包过严UID校验也已修复，最终服务通过保持连接的socket验证。

`3020` 必须是 `WORD room_handle + 81字节创建请求原样回显`。客户端复制这81字节，保留房间名、地图选择、模式、人数和时间设置，再发3550/12以及3070/14。原来的4字节room id不满足长度判断。

`3030` 是2字节创建错误码，`3080` 是18字节进房错误，均不能用来推送成功状态。`3070` 的成功回复为 `3100/245`：前96字节房间信息，后149字节自玩家元数据。房间编号是16位handle，当前单用户实验分配1；旧12100000常量不再用于建房。

`3100` 普通玩家分支要求slot<8；slot8会走旁观者处理。该分支从已登录客户端取自己的昵称、UID和1232字节外观，149字节尾部无需重新映射836字节持久角色。附加字符串保持NUL，未确定属性保持0；这些属性的完整语义仍需后续协议验证。

`2250→2270` 的长度是8+68*n；`2260→2280` 的长度是8+259*n，当前返回空列表。以前对2250发2500/1304、对2260发2580/8均是误映射。真实2500要求259字节且第4字节为1，2580不检查长度，直接通知界面，因此不能继续把它当空分页。

`20560`、`20564`、`2540/2550`、`2560/2570`不用于本轮竞技房间初始化；旧实验推送和fallback已撤下。`21410`是武器升级配置查询，不是已证实的进房前置条件。

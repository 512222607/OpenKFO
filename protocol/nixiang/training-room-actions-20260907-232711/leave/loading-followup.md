# 加载后续：4160、4180、4100 与战斗放行

范围和只读约束同 findings.md。未修改源码、客户端、数据库或服务。证据为 loading-*.json。

## 可直接用于决策的结论

1. **4100 不是加载成功回复，不要在 4160 后发送它。** Table 0x12ed8d8 的 4100 指向 raw 0x81a9b0；此函数不读正文，调用 sub_977E40(scene,0)。后者遍历 8 玩家，按每人 87 字节收集战斗统计，共 696 字节，并在 0x978498 发送 **4110/696**；还调用 P2P 清理。因此它是结果/统计上传请求，不能作开始。
2. **客户端真实加载完成通知是 4160/0。** sub_97DE10 读 scene+120，状态2等待 dword_17C87DC 加载标志后调用 sub_97C9C0。其末段 0x97d687→0x97d68f 调 sub_4A0FA0(scene,3)，随后 0x97d6ee push0、0x97d6f0 push1040h、0x97d6f5 call sub_A2CA00，即发送4160/0。此段已经反汇编精确验证。sub_97C9C0 整函数反编译报 switch information incomplete，保留报错并使用原反汇编，不修改 IDB。
3. **4180/0 是全员加载完成/恢复执行的强候选。** Table 0x12ed998→VA0x829770→raw0x819770；不读正文或长度；调用 sub_93CC70 刷新时间显示，mode controller vtable+36，然后 sub_4A0FE0(1) 写 gate byte+52=1。这与4160完成通知后的放行相符，但尚未有真实 wire 验证。不要说它独自等价于可玩。
4. **真正切入 scene state4 的明确网络 handler 是 8070。** Table 0x12ed9c8→VA0x82c4e0→raw0x81c4e0。存在 self 玩家时，handler调用 sub_9754E0、dword_17BAB78=1、sub_97B3B0(scene,1)，后者 sub_4A0FA0(scene,4)。随后会调用 mode controller vtable+28 开始模式。8070若为12字节会检查第一 DWORD 是否等于WORD room_handle，并把后8字节通过sub_807B10复制到room manager+785/+789；没有完整字段语义证据，不建议盲造计时值。
5. **8040/14 是开始屏幕/本地准备后的另一真实请求。** sub_964690 在正常self玩家路径调用 sub_975660；后者在0x9756b0发送8040/14，字段为 WORD room_handle + QWORD本地UID + DWORD dword_17BA718。因此真实进入地图后应观察8040，再实现其对应8070阶段，不能直接给客户端4100。
6. **4090 未找到可靠发送证据。** IDA immediate搜索4090/4160均零命中（4160经原始push另被证实，所以该搜索有漏报）；代码范围0x3f0000..0xc00000的32/16位push模式只有4160真实命中。先前4090 raw四字节命中0x98e942其实是CALL位移，不是opcode。不能因此宣称4090不存在，但不应推断其payload或响应。
7. **4170 不是本人加载成功ACK。** raw0x81adc0读取 QWORD UID，找其他玩家并更新其显示（自己UID则直接返回）；4180才是全局执行gate路径。

## 建议实现边界

- 先保持4030→4080/53的已恢复地图初始化链。
- 在session确实已开始加载、收到真实4160/0后，发送4180/0作最小静态支持候选；不提前推4100/411x结算消息。
- 保留session的loaded/started状态，避免重复4160反复触发开始；离房3110清掉这些状态。
- 观察4180后是否出现8040/14以及当前可见地图/开始提示。若出现8040，后续优先恢复8070；不要以只收到4160宣称训练已能操作。
- 若采用8070/12，第一字段格式由handler确定为DWORD room_handle，后8字节目前仅证明复制存储，尚未恢复语义；不能从8040未经分析就完整回显。

所有静态绝对表/虚表指针均按 VA-0x10000；相对CALL目的保留IDA解析值。

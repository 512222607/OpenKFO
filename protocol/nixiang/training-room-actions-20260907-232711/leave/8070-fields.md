# 8070 开局放行的最终字段与条件

本轮父任务实机反馈：4080后已加载场景，收到4160/0；一次4180/0后真实发8040/14，payload=0100e90300000000000000000000；用户反馈已经进场但角色不能动。这使8040→8070成为本次标准开局实际接续，不再仅是待观察分支。

## 可实施的12字节回复

- +0 DWORD room_handle：本轮为1，编码01000000。不是WORD+UID。
- +4..+11 八字节 round_context：**原样沿用同一轮4080 payload的 +45..+52**。
- 精确依据：4080 handler raw0x80e1a0在0x80e24c以payload+45调用sub_807B10；8070 handler raw0x81c4e0在0x81c597以payload+4调用同一函数。sub_807B10复制两个DWORD到room manager +785/+789；sub_422440只是返回this+785供后续网络包读取。
- 这8字节没有被证明是UID；不要用8040请求的UID去替换。
- 若当前4080末8字节均0，8070/12最小正确一致回复为 **010000000000000000000000**。
- 若4080使用非零上下文，则8070保持相同值，避免改变后续同步关联字段。

## handler的完整关键条件

raw0x81c4e0：
1. 如果room mode为0，额外调用sub_9758C0更新模式资源。
2. 如果没有本地玩家，调用mode vtable+144并退出。这种情形不直接走玩家控制state4。
3. 存在本地玩家：
   - payload非空且length==12且第一DWORD==WORD(room_handle)时，更新8字节context；
   - 上述长度/handle检查失败只会跳过context写入，**不会阻断之后开始流程**。
   - sub_9754E0把客户端当前tick记录到scene +128/+136/+272。
   - dword_17BAB78=1。
   - sub_97B3B0(scene,1)设置scene+140=1并将scene+120=4，启用实质游戏更新路径。
   - 设置其他界面状态；若mode controller存在且scene相关flag为0，调用mode controller vtable+28。
4. 因此空8070也可能推进，但正式实现应使用上述12字节一致格式，而不是依赖宽松检查。

## session处理建议

先验证8040长度14，解析WORD handle、QWORD uid、DWORD客户端附加字段；匹配当前已加载room session。只对同一session发一次8070，保持重复8040可幂等回放且不重复随机化context。不要从8040直接复制出12字节回复，因为布局不同。

这是静态协议和父任务实机请求证据；实际角色可移动仍需父任务发送后验证。

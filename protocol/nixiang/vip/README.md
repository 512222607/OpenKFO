## 历史：VIP商城配置基础（当时尚未改变游戏扣款）

根据85D37B..85D3A8确认普通购买路径对商品+30金币和+38点券分别乘1038+20支付比例后整除100；0走不额外打折分支，80表示八折。原生使用有符号DWORD乘法。新增vipShopPrice拒绝超过INT32_MAX的中间积及付费商品折后为0的组合，避免客户端溢出、服务器算出不同价格或意外免费；缺省币种价格0保持0。后续必须使服务器报价与扣款共同采用此规则，不能先单独发送非零1038比例。

新增VIPShopSettings支持总开关及白银/黄金/铂金0至100支付比例，独立版本及审计事务；vip_shop_settings_get/save贯通本地桌面及线上鉴权接口。TestVIPShopSettingsLocalDatabase在独立debug临时表实际通过4.175s，覆盖默认关闭、版本冲突、审计失败回滚、关闭保留数值、非法持久配置拒绝；价格边界及管理接口传递/鉴权测试通过。没有保存运行配置。

当前仅完成配置存储、管理API和纯计算；GM页面、游戏会员比例同步、真实购买/赠送扣款及改价/到期重报价仍待接入。原有1038继续零折扣，不能宣称VIP折扣已经生效。

当前客户端证据见receivers.asm（含PE哈希）。1038接收器A2C240严格要求28B；+0经9CCF50写当前对象+4C及+1063，+4起24B经9CCFC0写+1131。91C830刷新txtVip，使用9CCF80读取类型并交A342E0取文字：2白银VIP、3黄金VIP、4铂金VIP，其他分支显示非VIP。

83B3E0、8406F0、85D230通过9CCFA0取该配置块；+16正值参与商城价格计算，并与商品已有优惠价格比较。此字段不是已证明的剩余秒数。原生计算使用32位有符号乘法，服务端将来须独立校验范围与溢出，不能让客户端自报折扣决定扣款。

新增protocol.ParseVIPStatus及测试器1038诊断，保留未知字段，不自动下发或开放GM任意填写。尚需核实登录初始化、其他玩家资料/目录同步、其余权益字段、资格期限及服务器扣款一致性，不能只修改文字宣称VIP完整实现。

## 登录与VIP剩余时间面板

login-duration.asm进一步确认1020的+33 DWORD经9CCF50设置VIP类型，+32 BYTE是独立字段。1020不携带1038的24B权益块。测试器新增精确偏移及短包诊断。

VIP说明面板86D810调用9CE200，再将其第二输出除60、除24显示天数；这个输出并非直接来自1038权益块。9CE200扫描当前对象+EC8的记录集合，检查记录+5的730001/730002/730003及+19==1，分别提升结果类型到2/3/4；读取记录+13参与时间最大值比较。每一类型分支只在当前结果类型更低时执行，因此多卡场景存在遍历顺序依赖，不能简单称作所有卡的最长有效期。

该消费者中的时间被当作分钟换算，但仍须核对库存入站是否转换+13；现有服务端普通物品将该字段当作小时，不能直接把普通期限写法套到VIP卡。下一步应确认这些记录的入站来源/转换、商品类型及多卡取舍，才接GM资格发放和到期策略。

补充交叉证据：既有equip/permanent-report.md明确区分+19==0时+13为小时、+19==1时为分钟；与本次VIP消费者只接受状态1一致。因此差异首先来自记录状态，不能据此把所有库存期限统一改为分钟。旧永久报告仍需当前PE链核对，尤其在线倒计时及重新登录时服务器重新序列化的行为。

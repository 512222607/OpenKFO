## 续费提交与忽略提醒

新增当前PE有界证据：[renewal-requests.asm](renewal-requests.asm)。

8C2820发送1420/173B，前4B是原库存实例，后169B采用与购买相似的布局：

| 外层偏移 | 字段证据 |
|---|---|
| +0 DWORD | 原库存实例，来自窗口+580（124B记录+8） |
| +4 DWORD | 固定105，不能当作普通购买的109/111币种 |
| +8 QWORD | 本玩家UID |
| +58 QWORD | 同一个本玩家UID |
| +149 DWORD | 选中商品目录键，来自窗口+5FD |
| +161 DWORD | 客户端计算的金额；计算为窗口+61A乘+67C后有符号除100 |
| 其他 | 保留购买形态的字符串与未知字段；不是服务器授权来源 |

上述金额只能作为客户端申报值。原价、折扣资格、余额类型、可延长期限以及成功回执仍需完整核实；服务端不得按申报金额扣费，也不得把续费调用普通购买而生成新实例。

服务器已增加173B严格长度的`ParseRenewalRequest`，保留完整原始字节；统一日志在游戏通道C→S的1420上显示库存实例、目录键、申报金额、操作原值和双方UID，并明确“不代表已扣款”。这只是接收诊断，不授予请求中的UID权限。固定字节偏移、未知字节保留、输入隔离、错长拒绝及日志通道/方向隔离测试通过。候选Go服务器已构建，续费扣款业务仍未启用。

1440/4B传库存实例；1450的下游8BC8F0显示“删除道具的续费信息成功”，并说明仍可在仓库续费，然后调用8BC020。8BC020只在续费窗口+5B0集合内按记录+8匹配并移除条目，再刷新分页。此链证明的是删除提醒，不是删除背包物品或清除到期记录；不能将1450复用成1420成功回执。

## 1430实际回执与1510价目来源

[renewal-result.asm](renewal-result.asm)补齐静态注册数据：012FDDA0原始DWORD为1430、下一DWORD为1；B22DD6将826B30装入012FDDA8回调槽。包号已经位于PE数据段，不能因为未找到写入1430的MOV就认定没有该协议。

826B30读取+0 BYTE，非零表示成功，继续读取+1 DWORD库存实例并调用8BC1A0移除续费提醒，显示“恭喜您，续费成功！”；零表示失败，显示“续费失败！”。成功分支至少需要5B，失败分支至少1B；这只是已确认的读取下界，不宣称原始完整包长。服务器只读解析及日志已接入，短成功包拒绝解析，尾部未知字段仍由原始日志保留。不通过伪造成功回执推进未完成的扣费业务。

1510的823FD0将108B记录列表交85C040，并把首条传给8C2AA0；8C2AA0复制108B到窗口+5F4。因此提交中的窗口+5FD对应商品记录+9，窗口+61A对应商品记录+38（当前商城的点券价字段）。结合8C2820可确定申报金额取该字段乘折扣后除100，而不是从普通金币价+30读取。服务端续费资格、折扣和期限策略仍未接通，不能直接解除1500查询中的续费过滤。

## 同实例续期事务基础

InventoryManager.ExtendItem增加显式事务内的武器续期，不分配新实例、不覆盖强化/熟练度等其他字段。有限期限取服务器inventory_expirations；未到期从原截止时间累加，已到期从服务器当前时间累加。重置processed使下一次到期仍能处理，已过期道具恢复普通状态但不自动装备。永久物品、其他所有者、失效状态、非武器、零天数及超过3650天的剩余期限拒绝。

这是模拟器明确的期限策略，不宣称恢复原版计费规则。调用者必须锁账号行，并在同一事务完成资格/价格校验、扣款和幂等回执；当前尚未从1420接入，不能据此宣称续费已能使用。数据库临时表测试覆盖保留原实例与其他字节、到期和未到期、到期任务尚未执行、失败与回滚、所有者隔离、永久物品、VIP分钟字段隔离及溢出。

## 扣款与持久操作回执

ShopManager.RenewItem已把账号行锁、服务器价目/期限快照核对、库存归属及物品ID核对、点券扣款、ExtendItem和renewal_receipts写入合并为一个事务。当前明确采用有效点券商品的全价，不自行推测原版续费折扣。价目须由服务器提供并绑定会话，不能由1420携带；价格或期限变更后旧快照失效。

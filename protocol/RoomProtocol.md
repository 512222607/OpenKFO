# 房间协议（RoomProtocol）

> 更新：2026-09-18，基于 `b74129b` 后的房间修正。已对当前客户端静态反汇编核验，尚未完成原生多人实测。偏移默认十进制，详见[总索引与约定](protocol.md)。

## 1. 房间状态与完整流程

当前 S 状态：`lobby → room → loading → wait_ready → battle`。房间状态变更在 Hub 锁内串行处理，网络输出排队发送。

```text
C 2260 → S 2280                                      查询房间
C 3010 → S 3100 + 3160                              建房并直接安装房主
C 3070 → S 3100 + 3160 + 3105；老成员收 S 3090     加入已有房间
C 3230 → S 3250 + 4070                             换队、清准备
C 3200 → S 3220；必要时 S 4070                     当前设置保存行为
其他成员 C 4030 → S 4050                           准备
房主 C 4030 → 校验所有成员 → S 4050 + 每人 S 4080   开战/装载
每人 C 4160 → S 4170；全员完成 → S 4180             装载屏障
每人 C 8040 → 全员完成 → S 8070                    输入就绪屏障
C 3110 → S 3115；其他成员 S 3130                   退出等待房间
```

这张图是**当前实现**，不是原官方完整时序。资料中的 3020/3550/21370 等缺口见本文第 3 节。

### 1.1 C 2260 → S 2280：房间列表

C 发送：3B，`+0 u8 页码`、`+1 u8 刷新/方向参数`、`+2 u8 模式过滤`。资料发送点 `sub_92DD40`；S 允许 lobby/room：客户端等待进房结果 3100 时仍可能发送列表刷新，服务端提交进房后按正常查询返回 2280，不改变房间成员、准备状态；仍严格校验 3B 长度。页码小于 1 按 1，每页 9 条，按房号排序；过滤 `0x88` 表示所有模式；+1 当前只记日志，不改变排序。

S 2280：8B 头＋259B×条数。头 `+0 u32=1`、`+4 u32=本页条数`。每条当前填充：

| 偏移 | 类型/宽度 | 当前写入 |
| --- | --- | --- |
| 0 | u16 | 房号 |
| 2 | 21B | 房名 |
| 23 / 27 | u32 / u32 | 创建请求解析后的地图字段 |
| 31 | u8 | 有密码标志 |
| 33 | u8 | 创建请求 +33 |
| 39 / 40 | u8 / u8 | 容量 / 当前人数 |
| 41 | u8 | room 阶段=1，其他=0 |
| 42 / 43 | u8 / u8 | 创建请求 +35 / +36 |
| 44 | u8 | 模式 |
| 其他 | — | 零填充 |

资料正文支持 259B，但增补出现 103B 和“2260 不应答”的单机结论。当前多人实现使用 259B，有格式/分页测试；尚不能据该测试证明原生客户端消费完全正确。

### 1.3 C 3070 / 3075：加入房间

3070 为 14B：`+0 u16 房号`、`+2 u8 标志`、`+3 11B 密码`。S 当前只接受标志=0，要求 lobby 且未入房；相同房号且已在 room 时直接忽略重复请求。

失败回 3080：原 14B 请求＋u32 错误码（共18B）。当前码值：130=不支持的标志，29=房间不存在，30=不在等待阶段，32=满员，31=密码不匹配。通过后进入 install；绑定/P2P 校验失败会返回错误，而不是上述 3080。

3075 为 1B（资料发送点 `sub_9215B0`）。Go 将其解释为模式，0 表示任意；按房号选择第一个未加密、未满、等待中的房间。无合适房间时无应答。注意：这里 0 表示任意，而 2260 中 0 是具体模式，不能复用过滤语义。

### 1.6 C 3230 → S 3250：换队

C发1B，新队伍仅允许0/1；需处于等待房间。实际变化时设置Team并取消全房已准备状态；重复选择原队伍只给请求者回3250，不清准备。

S 3250为10B：`+0 u64 UID`、`+8 u8 Team`、`+9 u8 Spawn`。实际变化广播全房，原已准备成员另发4070。换队保留Spawn。

原生0x820160要求10B，+9传0x453950，+8传0x9E43F0。旧笔记把0x8202C0归给3250，实际该注册属于3160；不能据该函数推导换队会触发3201。当前Go未实现3201。

### 1.8 退出、踢人、房主变更

- C3110：0B。S leave(ack=true)，给退出者发3115（0B），其余等待成员收到3130（8B UID）。未在房间时仍补3115，使退出重试可结束。
- 房主离开等待房：选择剩余最小Slot成员为新Owner，广播3160（8B新Owner UID）；清剩余准备状态并发4070。
- C3140：9B，+0 u64目标UID、+8标志。只有房主在room阶段且标志=0可踢非自己的现存成员；先全房广播3150（原9B），再leave(target,false)，不会另给目标发3115。当前错误长度、非房主、非等待阶段、目标离开、踢自己、非零未支持标志均返回20150原因提示，保留房间状态与连接。
- 最后一个成员退出：删除房间。
- loading/wait_ready/battle期间有人退出：当前结束整局，其他人收到3115及20150说明，所有人回lobby，房间删除；不是断线重连或继续比赛实现。

3160实际注册到0x8202C0，长度8B，调用0x81BBE0设置房间对象Owner身份；旧“移除玩家”标题不适用于该消费者。

准备与开战的字段详解见 [BattleProtocol.md](BattleProtocol.md)。

## 4. 本轮证据与代码边界

客户端SHA-256：`98c43be72ac7600b368d4e185d75205376f79e938ea42e4b16ce8f8c4bae827b`。用本地PE静态反汇编核对注册指针与handler，没有运行或修改游戏客户端。

- 注册：0xB25BC5写3220，0xB25BD9绑定0x8205B0；0xB25B1F写3250，0xB25B33绑定0x820160；0xB25ACD写3160，邻近注册绑定0x8202C0。
- 0x81CF10按模式从记录+8/+10选择团队参数；+9与+8分别传入0x81CB00。3100团队分支0x8246BC读取+66。
- 0x820160将+9送0x453950、+8送0x9E43F0；两字段独立。
- 0x8205B0检查48B，地图调用0x81AA40，与3100消费一致；+46时间送0x81B8E0。没有按冲突笔记增加3100重放或21346替换。

`room_packets.go`负责布局及3200字段解析/编码；`rooms.go`负责权限、地图配置校验、状态转移与广播。全部账号快照成功后才提交入房。不引入额外数据库框架或配置驱动协议引擎。

`room_lifecycle_test.go`覆盖三人记录、装备尾步长、团队字段、设置权限/非法输入/重试、房主转移、退出重试、随机图建房重试。数据库真实两人测试需独立测试库。原生验收应覆盖：三人同房、队伍颜色、换队后换装、各地图出生点、设置同步、房主退出、踢人。包级测试与静态反汇编均不能代替以上验收。

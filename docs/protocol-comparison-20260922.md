## 优先结论

1. **观战未接入完整业务**：当前 Go `internal/game/rooms.go` 的 3070 分支对 Mode != JoinAsPlayer 返回 3080/error130。不是单纯缺一次刷新。Member 没有观战身份；room_packets.go 不填观战容量与观战人数，成员记录 +76 保持 0。
2. **观战入口不要认错**：参考实现使用 3070 的 +2 字节进入观战，用 3091/3092 在等待房间切换身份。Go 的 3071/3072 只是 WATCH_GAME 枚举和日志说明，不能以其名称替代已验证的入口。
3. **计分模式结算规则不同**：Go settlement.go 主要比较 HP 是否为零、剩余存活阵营；参考对 Mode0/1 使用生存判断，对 Mode2/3 使用击杀与惩罚计数，Mode16 使用专有积分。Go 的计分模式可能产生错误胜负。参考的计分公式仍是标注过的本地策略，不可称为官方奖励公式。
4. **房间列表筛选差异**：参考 2260 byte1=0 只列等待房间，=1 包括开战房间；Go 记录该字段但未用来过滤。3075 自动加入参考 136=全部，Go 目前用 0=全部，会与 Mode0 以及客户端 136 筛选冲突。这属于数据筛选问题，不能仅靠加刷新定时器解决。
5. **不要照搬退出逻辑**：参考只允许观战者离开而比赛继续，参战者战斗中退出仍把其他人全部 3115 踢回大厅。必须保留当前 Go 新增的团队退出修复。

## 战斗差异

- **8090 时钟 / 怒气**：参考 engine.py:poll_battle_clock 与 Go battle_clock.go 都采用每房间每秒递增8090，以驱动客户端被动气量；这支持本次修复方向。参考从elapsed=1首次发送，Go开战即1、随后elapsed+1，存在首秒偏移。1秒节奏在两边都属于本地策略，不是已确认的官方频率。
- **8127**：两边均确认63字节、+39角色、+51当前MP、+55房间及战斗序号。它是当前MP同步，不应直接当作“增加一整格气”。
- **8126 高优先级复核**：参考 layouts.py 把+39记为reporter、+47为target、+55为source；Go battle.go 注释及actorOffset把+55当目标、+47当来源。授权检查存在角色语义对调风险，应针对当前 gfld 的82B8D0及真实包验证后再改，不能直接拿 gfxz 参考覆盖。
- **已解码/转发范围差异**：参考还覆盖8125、8143、8144双角色变换、8270、8280、8284、8287、8293以及8400–8404子对象事件；Go battleMessage 的分发没有这些对应分支，通常落入battle_unhandled后忽略。参考“布局已解码”不等于“全部允许转发”，移植应逐项核对拥有者、对象登记、序号和上下文，不可整体放行未知包。
- **多回合**：参考包含8294–8297与4111/4112实验团队多回合，以及8155/8157 Mode16路径。当前Go未实现同等链路；不要把普通团队生存直接替换为实验多回合。
- **BUFF8150**：当前Go已有用户要求的兼容放行并记录审计；参考对部分跨角色BUFF仍忽略。两者权限策略不同，不应以参考覆盖现有行为，也不能从参考单测断言能解决所有BUFF。
- **序号**：两边都区分移动+15和普通事件+19；参考以发送者/通道维护序号，当前Go按事件种类与角色细分（已有NPC去重修复）。这是有意实现差异，直接替换可能重引入丢包/双扣血。
- **结果档案**：参考4120只在接收者自己的行携带完整profile，其他行profile留空；Go给所有奖励行携带profile，再排序把自己放最后。这与native按角色selector而非UID替换档案有关，值得单独回归，不应混入观战奖励路径。
